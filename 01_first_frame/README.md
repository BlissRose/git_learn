# 第 1 课：让第一帧跑起来

## 这一版要解决什么

假设 Sensor 刚交给我们一帧 8-bit 灰度图。我们暂时不接真实硬件，只用 12 个数模拟一帧 `4 x 3` 图像，完成三个动作：

1. 保存像素；
2. 计算全帧平均亮度；
3. 根据阈值给出“欠曝”或“可接受”的判断。

这就是 Mini Camera Pipeline 的第一个可运行版本。它很小，但数据流已经与真实影像程序一致：**帧数据 -> 统计 -> 决策**。

完整代码见 [main.cpp](main.cpp)。请先亲手编译运行，再继续阅读。

## 1. 程序入口与语句

```cpp
int main() {
    // 程序从这里开始执行
    return 0;
}
```

`main` 是普通可执行程序的入口。花括号形成一个作用域，分号结束一条语句。`return 0` 表示程序正常结束。

Android HAL 通常由 framework 通过接口调用，不会由你编写 `main`。但在开发 HAL 内部算法库、测试程序和复现工具时，`main` 非常常见。本课程先在可执行程序里验证核心逻辑，最后再接 HAL 边界。

## 2. 类型、变量与常量

```cpp
constexpr int kWidth = 4;
constexpr int kHeight = 3;
using Pixel = std::uint8_t;
```

C++ 是静态类型语言。变量在编译时就有确定类型：

- `int`：这里保存宽高；
- `std::uint8_t`：恰好 8 bit 的无符号整数，范围通常是 0 到 255；
- `std::uint32_t`：更宽的无符号整数，用作累加器；
- `double`：保存带小数的平均值。

`using Pixel = std::uint8_t` 给类型起了一个业务化别名。看到 `Pixel` 比看到一个孤立的整数类型更容易理解用途。

`constexpr` 表示值可在编译期确定，并且之后不能修改。固定格式、常量阈值和查找表尺寸里很常见。`kWidth` 这种 `k` 前缀是本课程采用的常量命名约定。

### 为什么累加不用 `Pixel`

12 个像素即使每个只有 255，总和也可能达到 3060，已经超过 8-bit 的 255。如果使用过窄类型，结果会回绕，亮度统计将完全错误。真实 4K 图像的累加更要先计算上限，并选用足够宽的类型。

## 3. 固定大小数组表示一帧

```cpp
const std::array<Pixel, kPixelCount> pixels{
    20, 30, 40, 50,
    40, 60, 80, 100,
    70, 100, 150, 190,
};
```

`std::array<T, N>` 表示包含 `N` 个 `T` 的固定大小连续数组。这里的像素在内存中连续排列，前三行代码也刻意排成图像的三行，便于观察。

`const` 表示这一帧构造完成后不允许再修改。本课只做统计，所以只读最符合意图。真实管线中，能只读就只读，可以减少误写和跨线程竞态。

`std::array` 适合本课的固定模拟帧；真实相机分辨率在运行时决定，第 3 课会换成动态容器。

## 4. 遍历像素

```cpp
std::uint32_t luma_sum = 0;
for (const Pixel pixel : pixels) {
    luma_sum += pixel;
}
```

这是范围 `for` 循环：从 `pixels` 中依次取出每个元素。循环体每执行一次，就把当前像素加到 `luma_sum`。

这里的 `pixel` 是一个值拷贝。单个像素只有 1 byte，复制简单直接。以后元素变成较大的帧对象时，随手复制就可能导致昂贵的整帧拷贝；第 2 课会引入引用。

## 5. 整数除法与显式转换

```cpp
const double average_luma =
    static_cast<double>(luma_sum) / static_cast<double>(pixels.size());
```

如果两个整数相除，小数部分会被直接丢弃。例如 `5 / 2` 的结果是 `2`，不是 `2.5`。这里先用 `static_cast<double>` 明确转换成浮点数，再做除法。

`static_cast` 是 C++ 中表达“我有意进行这种类型转换”的写法，比 C 风格的 `(double)value` 更醒目，也更容易被工具检查。

逐像素高性能路径不一定使用浮点数，因为吞吐、SIMD 和确定性都可能要求定点计算。但控制逻辑和统计代码里，先保证语义正确，再根据测量结果优化。

## 6. 用分支做曝光判断

```cpp
if (average_luma < kUnderexposedThreshold) {
    // 欠曝
} else {
    // 可接受
}
```

`if` 根据条件选择执行路径。真实 AE 算法远比一个阈值复杂，但 HAL 中充满类似决策：请求是否合法、buffer 是否可用、metadata tag 是否存在、当前状态是否允许 flush 等。

## 数据在程序里如何流动

```text
12 个 uint8_t 像素
        |
        v
uint32_t 累加器（避免 8-bit 溢出）
        |
        v
double 平均亮度
        |
        v
阈值比较 -> underexposed / acceptable
```

## 工程习惯：从第一天打开警告

编译命令使用了：

```text
-Wall -Wextra -Wpedantic -Wconversion
```

警告能尽早暴露隐式窄化、未使用变量和可疑语法。企业工程通常会进一步把警告当错误处理。不要习惯性忽略警告；先理解编译器在担心什么。

## 本课易错坑点

### 1. 累加器溢出

像素类型适合存一个像素，不一定适合存所有像素之和。选择累加类型前先估算：`最大像素值 x 像素数量`。

### 2. 宽高与数组元素数不一致

本课用 `kWidth * kHeight` 推导数组长度，减少三个数字各写一遍导致的不一致。真实场景还要处理 stride：一行占用的字节数可能大于 `width * bytesPerPixel`。

### 3. 整数除法悄悄丢精度

结果即使赋给 `double`，也无法挽回除法时已经丢掉的小数。转换必须发生在除法之前。

### 4. 把 `uint8_t` 直接输出成字符

在许多实现中，`std::uint8_t` 实际是字符类型，直接 `std::cout << pixel` 可能显示字符而不是数字。要打印单个像素，可写 `static_cast<int>(pixel)`。

### 5. 误以为数组就是图像的全部信息

真实 buffer 至少还需要像素格式、宽、高、stride、plane 布局和生命周期信息。后续课程会逐项加入，不能仅凭裸地址猜测这些属性。

## 练习

练习应直接修改一份自己的代码并运行观察，不要只在脑中回答。

### 练习 1：改变曝光结果

修改若干像素，使平均亮度不低于 90，验证输出变为 `acceptable`。记录你修改后的平均值。

### 练习 2：增加“过曝”状态

增加上限阈值 180。输出规则变为：

- 平均值小于 90：`underexposed`
- 平均值大于 180：`overexposed`
- 其余：`acceptable`

提示：使用 `else if`，并思考条件的先后顺序。

### 练习 3：找出最暗和最亮像素

遍历过程中再维护 `min_luma` 与 `max_luma`，最终打印二者。先用第一个像素初始化它们，避免随便选一个“看起来够大/够小”的魔法数字。

### 练习 4：亲手制造整数除法错误

暂时去掉两个 `static_cast<double>`，观察输出差异，再恢复正确代码。解释为什么最终变量是 `double`，结果仍然会丢失小数。
